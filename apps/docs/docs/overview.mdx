Lock closed GitHub issues and pull requests after a configurable period of inactivity, keeping resolved conversations from collecting stale replies.

## Why Use This Action?

- **Independent issue and PR settings** so you can apply different <Terminology title="How many quiet days before a closed thread gets locked" to="/docs/reference/terminology#threads-and-inactivity">inactivity windows</Terminology>, comments, and <Terminology title="The label GitHub shows on the lock, like resolved" to="/docs/reference/terminology#locking">lock reasons</Terminology> to each type.
- **<Terminology title="The note left on a thread right before it locks" to="/docs/reference/terminology#locking">Closing comment</Terminology> before locking** so contributors see why a <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">thread</Terminology> was locked and where to continue the conversation.
- **Label-based exclusions** so <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology> that should stay open for discussion aren't swept up by accident.
- **<Terminology title="Shows what would lock without touching anything" to="/docs/reference/terminology#locking">Dry-run</Terminology> mode** so you can preview which <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology> the search finds before anything changes. A live run rechecks each one and skips any that are already locked.
- **Detailed run logs** so you can see which <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology> were found and locked in each run.
- **Input validation** so a misconfigured value fails the run immediately with a clear error instead of producing unexpected results.

## How It Works

The action runs on a schedule you define in your workflow file. Each run searches for inactive issues and pull requests first, then comments on and locks each type in turn.

### Search

The action finds every closed, unlocked <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">thread</Terminology> in your repository that hasn't been updated within the configured <Terminology title="How many quiet days before a closed thread gets locked" to="/docs/reference/terminology#threads-and-inactivity">inactivity window</Terminology>. Issues and pull requests are scanned separately, each against their own day threshold, and up to 1,000 <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology> per type are processed in a single run.

### Comment

For every matching <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">thread</Terminology>, the action posts a <Terminology title="The note left on a thread right before it locks" to="/docs/reference/terminology#locking">closing comment</Terminology> explaining the lock. You can customize the comment text for issues and pull requests independently, or use the built-in defaults.

### Lock

Before commenting, the action reads each <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">thread's</Terminology> current lock state, because GitHub search can still list a just-locked thread as unlocked, and skips any thread that is already locked. It then comments and locks the thread with the reason you've chosen: `off-topic`, `resolved`, `spam`, or `too heated`. In <Terminology title="Shows what would lock without touching anything" to="/docs/reference/terminology#locking">dry-run</Terminology> mode, the action logs what it would lock without commenting on or locking anything.

## Getting Started

You can add Lock Inactive Threads to any repository in five steps.

1. Create a workflow file in your repository (e.g., `.github/workflows/lock-inactive-threads.yml`).
2. Add a `schedule` trigger with a cron expression for how often the action should run.
3. Pass `GITHUB_TOKEN` and configure the inputs that match your locking policy: inactivity days, comments, <Terminology title="The label GitHub shows on the lock, like resolved" to="/docs/reference/terminology#locking">lock reason</Terminology>, and any labels to exclude.
4. It's recommended to enable `DRY_RUN` for your first few runs to verify the action targets the right <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology>.
5. Once the preview looks correct, set `DRY_RUN` to `false` to start locking <Terminology title="Any issue or pull request the action can lock" to="/docs/reference/terminology#threads-and-inactivity">threads</Terminology>.

See [Usage](/docs/getting-started/usage/) for a complete workflow example.
